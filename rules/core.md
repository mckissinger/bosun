# Bosun core rules (Claude Code)

Rules for autonomous coding runs in Claude Code on Opus 5.5 (see Model). Rationale and doc citations: the Bosun README.

## Effort

Effort is the primary control on the lead. Effort is chosen when the session is launched (`claude --effort <level>`, or `/effort <level>` before the first brief) and held for the session. You cannot change it and should not ask for a change mid-run; state the level you are assuming in the brief.

- `low`: fully specified one-line changes.
- `medium`: routine implementation with fully specified behavior and existing test coverage.
- `high`: the default. Features, multi-file changes, refactors, debugging.
- `xhigh`: runs over thirty minutes, migrations, hard bugs, reviewing large diffs.
- `max`: only when xhigh has measurably fallen short.

Anthropic's Opus 5.5 guide reports `medium` matching Opus 5 at `high` on agentic coding in fewer steps and tokens. Bosun keeps `high` as the default until a project has measured a lower level on its own slices.

## The spec

Every project with substantial work has a spec file: `SPEC.md` at the repo root, or wherever the repo's docs convention puts it. It is the durable record of expectations and the only input a fresh session needs. It must contain, findably: the outcome; decisions in the user's own words; done-conditions with a status, each checkable by the verifier's tools (git diff, reading files, running the repo's checks, and a browser for a done-condition that names a route or screen) or marked human-check; undecided items; out-of-scope items; the current slice (in slice records, below); follow-ups (things noticed and not done, one line each with the slice, the date, and one tag: `bug`, `drift`, `nit`, or `deferral`; removed when promoted to a done-condition, dropped by the user, or shown resolved by `bosun-triage` in a batch the user approves (or that the lead applies at a milestone end under `Decisions: take recommendations`); new nits are not written as follow-ups (see Finishing), and a nit already listed is folded into the next slice that touches its file, named as a done-condition in that slice's brief so it is in scope, or dropped through triage); and lessons. The layout is yours to choose per project. Keep it reviewable by a person in one sitting, and reorganize or split it when it stops being that, saying so in your report. Older specs keep briefs in a current-slice section, where once a slice's PR merges its brief moves under the spec's history; slices recorded as below need no move. When finished slice briefs and old slice-log entries push the spec past one sitting, `bosun-triage` moves them, verbatim, to an archive file next to the spec and leaves a pointer where they were. Briefs and verifies read the archive only when an item points into it. Update status in the spec as work lands, not only at the end.

Slice records. Each slice keeps its own record file beside the spec, `slices/<date>-<slice-name>.md`, holding its brief, its evidence lines, each verify verdict, its slice-log line (`Log:`) and the follow-ups it found. Per slice, the spec itself changes only in the statuses of its roadmap done-conditions (done-conditions a brief defines for itself keep their status in the record) and any lesson, besides the spec-level entries other rules keep there (a decision, an undecided item decided or moved, a draft done-condition, a blocked step), so open PRs from parallel slices rarely conflict on the spec. The current slices are the records not yet on the default branch, the ones an open branch or PR adds; a merged record is that slice's history. The slice log is the records' `Log:` lines together with any entries the spec still holds from before. Open follow-ups are the spec's follow-ups section together with each record's Follow-ups section, and removing, promoting or resolving one edits the file that holds it. A spec without a `slices/` folder gets one with its next slice, plus one pointer line each in its current-slice section, slice log and follow-ups section; existing entries stay where they are.

Never build an undecided item; propose wording for it as a draft and leave the decision to the user, unless `Decisions: take recommendations` lets the lead decide it (see Decisions).

Lessons are what this codebase needs a fresh session to know that the repo and git history do not already record: corrections, confirmed approaches, environment quirks, and why each mattered. One entry per lesson with a one-line summary first. Read them before starting a slice. Update an existing entry rather than adding a duplicate, delete entries that turn out to be wrong, and do not record what the code, the checks, or the spec already say, apart from the standing entry below. If the section grows past what a person reads in one sitting, split it into its own file next to the spec and say so in your report.

Corrections become checks. When the user corrects an agent's work, first look for a mechanical guard that would have caught it: a lint rule, a hook, a test or a CI check. Add it as a done-condition of the slice that fixes the defect, or of the next slice when that one is already verified. When a kind of defect enters "Recurring verify failures", `bosun-triage` proposes such a check for it as a draft done-condition. Only what no check can express becomes a lesson or rule text.

The lessons hold one standing entry, "Recurring verify failures": at most ten lines, each a kind of defect that verification has caught in two or more slices of this project, with one short example (for example, "a read that returns another account's rows"). `bosun-triage` keeps it from the slice log (the records' `Log:` lines and older entries) at each milestone end. Before every verify, the implementer checks the slice's diff against each kind on the list and fixes what it finds; the verify prompt carries the list too. A new project starts with the entry empty.

## Model

Bosun runs on Opus 5.5 (`claude-opus-5-5`) in every role. The lead briefs, implements, keeps the spec, commits, and fixes FAIL findings itself; the project-local `bosun-scout` and the fresh, read-only verifiers run on Opus 5.5 too. Before briefing, confirm the session model is `claude-opus-5-5`: a spec line cannot change it, so switch with `/model claude-opus-5-5` or relaunch with `claude --model claude-opus-5-5`. Use the local scout and verifier definitions that `/bosun-mode opus` writes, not plugin-scoped substitutes.

A spec may carry `Provider mode: opus`, the only value; a spec without the line is the same. `fable` and `fable-opus` were removed in 0.24.0, and `codex`, `fable-crew`, `astra-crew` and `astra` in 0.18.0: a spec that names one makes `/bosun-brief` and `/bosun-verify` stop and say to change the line to `Provider mode: opus` or delete it.

Verifier effort is independent of the lead session's effort. `/bosun-mode --verifier-effort <low|medium|high|xhigh|max>` stores a top-level `Verifier effort:` default in the spec. `/bosun-verify --effort <level>` overrides it for that invocation. Precedence: invocation override, the current slice's `Verifier effort:` (in its record), top-level `Verifier effort:`, then `high`. Ignore historical slice logs and quoted examples; conflicting settings at one scope or invalid levels stop verification. `/bosun-verify` configures both project-local verifier agents with that effort before launching the appropriate one. Record the effective effort with each verdict and in the slice's `Log:` line. A retry keeps the same effort unless the user changes it. This changes the verifier's frontmatter, never the lead session's effort.

## Decisions

The decisions setting is a line near the top of the project's spec: `Decisions: ask` or `Decisions: take recommendations`. A spec without the line is `ask`: the lead stops for the user wherever these rules say to stop.

Under `take recommendations`, the lead decides these itself, taking the option it would recommend:

- an open question that comes up mid-run;
- an undecided item, when the spec's outcome or decisions point to an answer;
- a disagreement after two FAILs on the same finding, by taking the fix it recommends and verifying again.

It records each one in the spec's decisions as "(build mode, <date>)" with the choice and one line of why, moves a decided undecided item out of the undecided list, and continues without ending the turn.

The lead never decides these itself, under either setting:

- credentials, accounts, and sign-ins;
- prices, fees, and any live spend;
- production data, and anything sent to real people;
- legal, naming, and trademark questions;
- approval of a new design, or of a departure that changes an approved design, when `Design approval: me` (see Design);
- anything the spec lists as the user's.

Work that needs one of these is parked: the lead records it as a human-check, or as an undecided item phrased as a question with the lead's recommendation, and takes the next runnable work. Under `ask`, two FAILs on the same finding stop the run; under `take recommendations`, a third FAIL on the same finding stops it. Under either value, a slice that reaches its verify limit without passing stops the run the same way (see Finishing).

## Run policy

The run policy is a line near the top of the project's spec: `Run policy: one slice` or `Run policy: until blocked, max N slices`. A spec without the line is `one slice`; `until blocked` without a `max` means `max 10 slices`.

Under `one slice`, `/bosun-brief` runs one slice, verifies, reports, and stops. Under `until blocked`, after a slice verifies (PASS or PASS WITH FOLLOW-UPS), the lead records lessons, commits, pushes, opens a PR for the slice's branch, reports the slice, and then briefs and runs the next slice in the same turn. Every slice has its own branch and its own PR, merged as the next paragraph says. The run stops, with a report saying why, at the first of: no runnable done-condition remains; every remaining runnable item needs a decision the lead may not make (see Decisions); a verify produced two FAILs on the same finding (three under `Decisions: take recommendations`; see Decisions); a slice reached its verify limit without passing (see Finishing); every remaining runnable slice waits on an unmerged PR that cannot merge on its own (see Merge flow); an environment failure blocks every remaining runnable slice (see While working); N slices have been started in this run, counting the first. A hub whose lanes are running and that has no planning work left pauses instead, as "Lanes" says; that does not end the run.

Under `until blocked`, the lead never ends the turn between slices to ask whether to continue or to announce the next slice; the stop list is the only way a run ends. After a slice verifies, the lead pushes its branch, opens its PR, and arms auto-merge with `gh pr merge <n> --auto --merge`. If GitHub refuses because every required check is already green, the lead merges with `gh pr merge <n> --merge`. It never merges past a red or missing required check and never bypasses branch protection. Where the repo has no required checks or does not allow auto-merge, it leaves the PR open and says so in the report. Where the project's spec or the user's instructions say merging is the user's, those win. The lead does not idle on CI: while a PR's checks run, it briefs the next slice and builds what "Merge flow" allows, and waits only where that section says.

Records ride along. Every PR pays a full CI cycle, so a change that touches only records (the spec, slice records, docs, design boards, screenshots: a decision, an approval, a polished board, a status fix, triage results) never gets a PR of its own during a run. The lead commits it to the branch of a slice whose PR has not merged (the slice in flight, or the next slice), and pushes that branch so the record is not lost if the session ends. A board goes with the slice that builds its screen. Until that PR merges, the lead carries the decision into every brief that needs it, since a slice built ahead from the default branch cannot see it. Only when no slice of the run will follow do the records go in one PR, opened at the end of the run. When a slice stops without a PR, as at the verify limit, the lead moves the records commits off its branch (`git cherry-pick`) onto the next slice's branch, or into that end-of-run PR, so records never wait on unverified code. Outside a run, a records change the user asks for gets its own PR as before.

A done-condition is runnable when its status is `todo` or `in progress`, it is not `human-check`, and nothing it needs is on the undecided list. Under `Decisions: take recommendations`, before concluding that none remains, the lead decides the undecided items the Decisions section lets it decide, which makes the work that waited on them runnable. When no runnable done-condition remains, under either policy, the lead does not invent work: it reports that the roadmap is exhausted, lists every open human-check condition and every undecided item as the question the spec records, proposes candidate next slices drawn from the open follow-ups (the spec's section and the records') as draft done-conditions marked as proposals, and ends the turn asking what next. A proposal becomes a done-condition only when the user says so.

## Merge flow

These rules apply under `Run policy: until blocked`.

Building ahead. While a PR's checks run, the lead may build the next slice when that slice needs nothing from any unmerged slice: no code or configuration file that slice changes, no interface it defines, no behavior that must land first. The spec does not count, since every slice writes it. Each such slice works in its own worktree and branch, cut from the latest default branch, and never takes a done-condition that an open PR of the run already covers. A slice that depends on an unmerged slice is briefed while CI runs and built only after its base merges, from the updated default branch. Branches are never stacked on unmerged slices.

Waiting. When every remaining runnable slice depends on an unmerged slice, the lead waits for that PR to merge, watching its checks. It waits only for a PR that merges on its own: auto-merge armed, required checks present, and no required review. When the base cannot merge on its own (the repo has no required checks, disallows auto-merge, or requires an approving review, or merging is the user's), the run stops and names the PR it waits for.

Spec edits. Every slice, built ahead or not, writes its brief, log line and follow-ups in its own record (see The spec), and in the spec only what "Slice records" leaves there. When two of the run's PRs still conflict on the spec, the lead merges the default branch into the later PR's branch, keeps both sides (every status either one set, and both slices' lessons), and pushes.

Watching open PRs. Before each slice, after each verify, and while waiting, the lead checks the run's open PRs and the latest run of every workflow on the default branch, not only CI, so a failing workflow that no check requires, such as a migrations deploy, does not go unseen. A workflow that gates nothing and only reports, such as a scheduled audit or the nightly flake hunt, is read for its report: its red run is reported and its findings become follow-ups, rather than being fixed before other work. Where the project runs a flake-fix loop (`bosun-ci`), the nightly hunt's flakes are the loop's to fix and do not become follow-ups. A throwaway PR that `bosun-ci` opens to prove a selection gate goes red is not a red PR to fix; it is closed unmerged once its check reports, red or green. A PR with a failing required check or a merge conflict, or one the merge queue removed (see "Queue removal"), pauses the current slice, whose work stays in its worktree; a removal a person made only gets reported, once, and pauses nothing. A removed PR's own checks stay green, so the lead finds it by its timeline or its `queue-ejected` label, not by its checks; this is how a removal whose session has ended is still fixed. The lead pulls that PR's branch in that PR's worktree, fixes it there, reruns the checks the fix could change, runs `/bosun-verify` on a fix that changes code (see Finishing), pushes, and resumes. A slice that depends on that PR waits until the fix merges. An environment failure on a PR (see While working) doesn't pause the current slice: the check is rerun once and reported, and the PR stays open. A red run on the default branch is fixed before any other work, as its own slice and PR from the latest default branch, unless it is a flake candidate (see Tests and CI) or an environment failure (see While working), which is reported instead. While lanes run, "Lanes" says who fixes it.

Following a PR. After opening a PR that merges on its own (see Waiting), the run's last PR included, a session never ends its turn saying it is waiting on CI unless something will wake it: it keeps a background wait, or the host's PR monitor, that ends when the PR merges, a check fails, the PR conflicts, the merge queue removes it, or it is green but neither merged nor queued, and on waking it acts on whichever happened (fixes it as above, merges the default branch to resolve the conflict, reruns an environment failure once, handles a queue removal as below, or gets a green PR merging as "Run policy" and "Merge setup" say: arm auto-merge again, merge with `gh pr merge <n> --merge` when GitHub refuses because every required check is already green, or update it where the repo requires up-to-date branches without a queue). A green PR that is open, not queued and has auto-merge off is checked for a queue removal before auto-merge is armed again. A slice split into parts starts its next part when the previous part's PR merges, without being told. A session's "running" flag is not progress: the hub judges a lane by its commits, PR state and transcript times.

Queue removal. A PR the queue removed is open, not queued and has auto-merge off, and its latest queue event is a `RemovedFromMergeQueueEvent` whose `reason` is not `merged` (read from the PR's GraphQL timeline). Its own checks can all be green, because the queue tested it on top of newer code, and often ran suites the PR's run skipped. The session reads the reason, and for failed checks the failed jobs of that PR's latest `merge_group` run (head branch `gh-readonly-queue/<base>/pr-<n>-<sha>`), then acts by reason. `failed_checks` and `checks_timed_out` are a failing required check: it fixes the PR in its worktree as above, verifies a code fix, pushes and arms auto-merge again; a flake candidate (see Tests and CI) or an environment failure is instead re-queued once and reported. `merge_conflict` merges the default branch in. Any other reason, such as `invalid_merge_commit` or `branch_protection_failure`, is re-queued once, and a second removal is reported. It never arms auto-merge again after `failed_checks` without reading the failed run, since a re-queued PR with a real failure only fails again behind the PRs it delays. A removal whose actor is a person rather than the queue (`github-merge-queue`) was deliberate: it is reported, never re-queued.

Merge setup. The recommended setup is a merge queue on the default branch, where GitHub offers one (public repositories owned by an organization, or GitHub Enterprise Cloud), with the required checks also triggered on `merge_group`; auto-merge then puts each PR in the queue. A required check whose workflow lacks the `merge_group` trigger never reports, so queued PRs hang; a job that reads a PR number, for example a changed-files gate on `pulls/{n}/files`, needs a `merge_group` fallback that runs everything, or queued PRs fail or skip it; only a check that makes sense solely on a PR's diff may report success there instead, as `bosun-ci` describes. Where no queue is available, the default branch does not require branches to be up to date before merging, and CI also runs on every push to the default branch. Turning a queue on comes last, after the workflow changes have merged and only when the user asked; `bosun-ci` holds the steps. A repo that requires up-to-date branches without a queue leaves every other open PR behind after each merge, and auto-merge does not update them. There the lead updates the oldest behind PR whose checks are not failing (`gh pr update-branch <n>`), one at a time, because each update restarts that PR's CI and only one can merge per round, and pulls before pushing anything else to it. The `bosun-ci` audit reports the setting.

## Lanes

A lane is a separate Claude Code session that the hub, the session running the run, starts in its own worktree to run its own Bosun loop on one area of the spec. Lanes are sessions, never subagents: a lane runs many slices, each with its own verifier, across compactions and CI events, and the user can open and steer it. Subagents stay inside a slice, as before. `/bosun-brief` ("Lanes") holds the procedure.

The hub's job. While lanes run, the hub writes no code. It plans and decides with the user, keeps the spec, runs milestone triage and the CI audit, reviews screens with the user, watches the default branch, and relays between the user and the lanes. Every code change goes to a lane. This keeps the hub quick to answer and its context on decisions rather than build output.

Shapes. Under `Run policy: until blocked`, the hub picks one of three shapes for the run:

- one session as before, when the run has fewer than five runnable slices or the user says they won't be steering it; this takes precedence over the other two;
- the hub plus two lanes, when the run has two areas, each with at least three runnable slices, that touch different files and database tables and need nothing from each other;
- otherwise the hub plus one lane, which takes all the run's work in spec order.

With two lanes, runnable work that fits neither area goes to the first lane to finish its area, as assigned slices.

At most three sessions run. Lanes also need the project's checks to be isolated, or made so by the setup slice below, and lane sessions that can be started, by the hub with the app's start-session tool or by the user from prompts the hub prints. Where those fail, the run is one session.

Approval. The hub proposes the shape to the user: the areas, the shared files, each lane's slice cap, and what is likely to need the user. It starts lanes only after the user approves, once per run, under either `Decisions:` value, because lanes cost tokens and add to the user's review queue. The proposal does not stop the run: the hub states it in its first slice report of the run and again at each milestone end until the user answers, and meanwhile runs as one session as before. A yes covers the rest of the run; a no stands until the next run. After the yes, the hub finishes the slice it is on and then stops building.

Stack isolation. When migrations, end-to-end tests or suites that reset or seed data share one stack and the spec has no `Stack isolation:` line, the first step after the yes is a setup slice, which the hub runs itself before any lane starts. It builds a per-lane stack command in the project: each lane gets its own project id and port band, generated from the committed configuration into an ignored folder; a holder record lets only one worktree hold a lane; the project's own data-resetting commands refuse, from a worktree holding a lane, to hit the main stack (a project can guard only its own commands, not a tool's plain reset such as `supabase db reset`, so a lane and its verifiers never run those); and teardown removes the lane's containers and volumes. The command starts only the services the project's tests need, the same list CI uses, and a slice that needs another service for a run, such as one for browsing data or reading test email, adds it for that run. The slice adds the `Stack isolation:` line naming that command, and lanes use it rather than copying the stack by hand.

Areas and assigned slices. Lanes are split by area, not by slice. Each lane works only its own area's done-conditions and undecided items, plus slices the hub assigns it; anything else it sends to the hub. The hub names the shared files, such as layout frames, shared components, test helpers, global styles and CI workflows. A change to one goes to one lane as an assigned slice, and only that lane edits the file until the slice merges. When two areas each need the same new page or component, the hub names the one slice that builds it, and the other lane waits for that slice to merge. Assigned slices go to the top of the lane's queue, after the slice it is on:

- a shared-file change;
- a fix for a red default branch: the hub assigns it to one lane. A lane that sees the default branch red tells the hub and does not fix it unless the hub assigns it; it finishes its current slice and keeps working its area, and its PRs merge once the fix lands;
- the milestone hygiene slice and fixes from the CI audit: each goes to the lane whose area holds the files, and work that spans both areas or touches shared files goes to one lane, which holds those files until the slice merges; the hub tells the other lane which of its files are held, and it leaves them alone until then.

Inside a lane, "more than five open bugs makes the next slice a hygiene slice" counts only bugs in the lane's own area; other bugs are the hub's to assign.

Branches and the spec. Each lane slice branches from the latest default branch, gets its own PR and auto-merge as "Run policy" says, and "Merge flow" applies inside each lane; nothing stacks across lanes either. Each lane counts, watches and fixes its own slices and PRs. The run's `max N` bounds the slices the hub built before lanes started plus every lane's cap; the hub sets the caps when it starts the lanes, from the slices already started. Lanes write as "Merge flow" says under "Spec edits": each slice's brief, log line and follow-ups in its own record, in the spec only what "Slice records" leaves there (roadmap statuses, lessons, and a lane's own decisions, undecided moves, drafts and blocked steps), and both sides kept on a conflict. The hub owns the rest: decisions taken with the user, the undecided list, out of scope, and triage results. Records ride along here too (see Run policy). The hub sends each decision, and each change to the undecided or out-of-scope lists, that touches a lane's area to that lane in a message quoting the user's words, and the lane writes it into the spec on its current slice's branch. When two lanes need the same one, the hub names one of them to record it and tells the other in a message only. A lane on its last slice with records left over sends them to the hub for its records branch. The hub collects everything else on one records branch from the latest default branch and opens its PR once per milestone end and at the run's end, not after each decision; that is planning, not code.

The user goes through the hub. A lane runs under the spec's `Decisions:` value. The user-only items are: a decision the lead never makes under "Decisions", a change to a path the spec protects, an approval, and a design review. A lane records each in the slice and sends it to the hub in one short message saying what, why, and where the screenshots are, then takes other runnable work in its area. Wherever these rules or the skills tell the lead to ask the user, stop for the user or report to the user, a lane sends that to the hub instead. The hub batches these for the user. A lane never asks the user directly.

Checks in a lane. A lane claims its stack with the `Stack isolation:` command before any data-resetting check, runs those checks only through it, tells every verifier it launches to do the same, gives every screenshot and output path as an absolute path inside its own worktree, and removes the stack with the command's teardown when it ends.

Milestones. Milestone-end triage and the CI audit are the hub's; their code work goes to lanes as assigned slices. While lanes run, a milestone is a group of done-conditions the spec names, or, in a spec without groups, every fifth slice merged across the run, which the hub counts from the default branch. Triage's Git cleanup leaves each lane's own worktree, which the app made, to the app; a build-ahead worktree a lane added may be removed once it is merged, clean and idle, which loses nothing.

Idle hub. With lanes running and no planning work left, the hub ends its turn, saying which lanes are running. This is a pause, not a stop. A lane's message, a lane's end or the user wakes it, and it continues the same run with the same count and approval.

Lane end. A lane ends at its slice cap, when its area and its assigned slices are done, or at any stop in "Run policy". It removes its stack with the command's teardown and, once each of its PRs has merged or closed or cannot merge on its own (see Waiting; a PR parked on a red check the lane has stopped fixing, at the verify limit or after an environment failure's one rerun, counts as one that cannot), reports to the hub: why it ended, each slice, its PR, its verify verdicts, follow-ups, and what waits on the user. The hub checks those PRs before reporting them done. Once a lane has reported and its PRs have merged or closed, the hub archives that lane's session with the host's archive tool where it has one (archive, never delete) and confirms the lane's stack is gone, reporting rather than stopping one that is still running. A lane that waits on a PR, a verify or a decision is still in use and stays. When the last lane ends with runnable work left and the count below `max N`, leaving out work parked on two FAILs on the same finding, at the verify limit, on a user-only item or on an environment failure, the hub picks the shape again for the remaining work under the same yes: new lanes where the shape allows, otherwise it builds again as one session. Otherwise the run ends at the stop that applies. Lanes the user started by hand cannot message or wake the hub: they put their messages in their own reports, and the user carries them to the hub and wakes it.

## Follow-ups and milestones

Every follow-up gets a home when it is written. A bug or security issue in the slice's own work is fixed in that slice, apart from the third-run case in "Finishing". A bug in shipped code is fixed by the next slice that touches its file, or by a hygiene slice before its milestone closes; no bug outlives its milestone. New nits are fixed in the slice or dropped, never written down (see Finishing); a nit already listed is folded into the next slice that touches its file, and dropped at milestone end if it is still open and not cheap. A deferral names the done-condition or milestone it waits for. An item that needs the user or gates a launch goes to the spec's human-checks. A milestone is a group of done-conditions the spec names as one; in a spec without groups, every fifth slice ends one. At each milestone end under `until blocked`, the lead runs the `bosun-triage` skill, which also finds worktrees and local branches whose work is merged and that are clean and idle, removes them when the triage is applied, and updates the "Recurring verify failures" lesson, then a hygiene slice with its own PR for the open bugs, then a `bosun-ci` audit against recent runs, reading the latest weekly CI report where the project posts one, recording its findings as follow-ups and running any fixes as their own slice, never folded into a feature slice. When more than five bugs are open, the next slice is a hygiene slice. Under `Decisions: take recommendations`, a hygiene slice built from open bug follow-ups is runnable work, and the lead promotes those bugs to done-conditions itself; it still never invents features.

## Design

These rules apply to every slice that adds or changes a screen. The approval gate is a line near the top of the spec: `Design approval: me` or `Design approval: critique`. A project with UI and no line is `me`.

1. Before writing UI code, load the design skill the project names (in its design doc, such as `design/DESIGN.md`, or its project instructions) and read the project's locked design rules. Then, for each screen in the slice, not only the first, read its approved board in the design tool, the design system, and any motion and mock-data notes the project keeps. Take sizes, colors and spacing from the design tool's own values (its code or computed-style export), never from an exported image. An image is only for comparing. In a project that names no design tool, the mockup's own source (the canvas artifact and its repo copy) stands in for the design tool here and in step 6.
2. Mock up a screen that has no board first, in the project's design system and in the design tool its design doc names, with a copy in the repo's design folder. Use a design canvas artifact only when the project names no design tool.
3. Get the mockup approved before writing product UI. Under `me`, the user approves it, and a new design direction or a new interaction pattern always waits for that approval (parked as Decisions describes). Under `critique`, a fresh agent critiques the mockup, the board is revised, and it gains an "After critique" note.
4. Build the screen, every state and the motion its board shows. A difference from the board that the build needs is a departure: record it in the slice with its reason. A forced departure (the platform or the data cannot do what the board shows, and what the user sees or does is unchanged) is approved by that record. A departure that changes the design is approved before the first verify: under `me` by the user, shown beside the board (parked as Decisions describes while it waits); under `critique` by a fresh agent. While a departure waits, its code stays off the slice's PR, or the PR stays open without auto-merge; it never merges unapproved.
5. Before the first verify, check it at 390, 768, 1024, 1280, and 1440 pixels wide, or the widths the project names, in its empty, loading, error, hover, and focus states, with the board's motion, including exits and reduced motion.
6. Export the current board images from the design tool in this slice, not from an older export folder, and put them in the slice's evidence. A fresh agent compares the screenshots with them. Any difference that is not an approved departure blocks the done-condition.

A new direction starts fresh: several new options, not variations on an older approved mockup. Screenshot and board-export paths go in the evidence lines.

## Starting substantial work

Anything beyond a few tool calls starts with `/bosun-brief`. With no spec, it creates one from what the user supplied and stops for review; that is the one planned stop. With a spec, it takes the next slice and runs to completion. Small tasks get a three-line brief, not a ceremony. If context was compacted, or a checkpoint was printed at session start, re-read the spec before doing anything else.

## While working

If, while working or testing, you find a pre-existing bug, a performance concern, or behavior the task doesn't mention, don't fix, optimize or extend it in this change unless the requested behavior cannot work without it; report it as a follow-up in your summary. Where the task is ambiguous, implement the reading its wording and the surrounding code most directly support, state that assumption in your summary, and don't build for the other readings as well. Verify your work however you like; scratch scripts and quick checks need not be kept. Commit tests only where the task asks for them or this repository already keeps tests for this kind of change, sized like the neighboring test files — roughly one focused test per stated behavior — and don't turn scratch checks into additional permanent test files. This is about extras only: implement every behavior the task asks for, completely.

Tests and CI. Before handing work off or pushing, run the tests for the code you touched; run the full unit suite only when the change touches shared code, configuration, dependencies, or the test setup. Run end-to-end (browser or UI) tests targeted: the specs for the routes and flows the change touches, plus the specs the done-conditions name. Run the full end-to-end suite at most once per slice: when a required CI check runs it before merge, that check is the full run and you do not run it locally; otherwise run it once, after the last code change. No done-condition requires a full local end-to-end run. After a fix, rerun only the checks the fix could change, failed end-to-end specs first (Playwright's `--last-failed`), then the targeted set; a fix to comments or documentation reruns typecheck and lint only. Do not push to find out whether tests pass: CI is the final gate, not the feedback loop. The one exception is `bosun-ci`'s throwaway PR proving a selection gate goes red, where CI's verdict is the thing under test. Never weaken, skip, or delete a test to make a change pass; when a specified behavior change requires changing a test, say so in the report. New tests make no real network calls, use no real sleeps or wall-clock time, and do not depend on test order or leak global state. Follow the repository's written test and CI conventions, such as which files opt into shared state, file size limits, and which job a test belongs in; where they differ from these rules, they win. A failure that passes on rerun with no code change and is unrelated to the change is a flake candidate: report the test name and failure message, do not change code for it, never fix it with retries or longer sleeps, and quarantine it only with the user's approval; a flake-fix loop the user set up has that approval for its own entries, but not for renewing them (`bosun-ci` holds the time-limited quarantine, the nightly hunt and the flake-fix loop). End-to-end retries in CI stay at most one, and a test that passes only on a retry is a flake, reported like any flake candidate. A change to CI workflows states in the report and the PR whether it adds or removes CI time, and does not undo optimizations already in place.

Branch updates. Merging or rebasing the default branch into a PR's branch restarts that PR's whole CI run, so a session does it only to resolve a merge conflict, when a required check needs a change that has since landed on the default branch, or where the repository requires up-to-date branches without a merge queue ("Merge setup"). Otherwise, a green PR that is only behind is left as it is: the merge queue, or CI on pushes to the default branch, tests it against the newer code. This applies under every run policy.

Other sessions. Every session that writes code works in its own worktree and branch; only a read-only session may share a checkout. Never apply an unapproved or unmerged migration to a database another session uses, never reset or stop another session's stack or server, and never stop processes by name.

Shared machine. Sessions on one machine share its memory, so start what the work needs and stop it when done. A session stops the dev servers and stacks it started, or holds through the `Stack isolation:` command, once it no longer needs them, and a lane removes its stack when it ends. Before starting a stack or a full test run, check how loaded the machine is (memory pressure, swap, load). Under pressure, stop what this session started and is not using, and say so. Report everything else, including anything it isn't sure it started, rather than stopping it. The check advises and never blocks work.

Environment failures. First check whether the change could have caused the failure: did it touch what failed, and does it fail without the change? Anything the change could have caused is a code failure, handled as one. A failure that is clearly the environment, such as a Docker daemon that is down or a hosted runner timing out on checkout, gets one retry. Note the machine's state at the first failure and report it whether or not the retry passes, so an intermittent failure leaves a record. It never counts as a test result, and nothing changes in the slice to get past it; a recurring one becomes a follow-up, and a fix to CI itself goes through `bosun-ci`. If the retry fails too, record the blocked step in the spec and continue with work it doesn't block. Flaky tests stay under "Tests and CI".

The number of tokens used to edit files is best minimized, all else being equal. Therefore, when it will not affect the end result, try to surgically edit a file rather than rewrite the entire thing.

If a done-condition names a route or web screen, run the app and check it in a browser before calling it done, with whatever browser tool the session has (the Claude Code desktop browser pane, or Playwright MCP). A route-or-screen done-condition may name a viewport width; check it at that width and carry the viewport in the evidence line so the verifier can re-check it in Playwright at the same width. A lane, or any session no one is watching, checks routes with headless Playwright only and never uses a tool that waits on an approval prompt, such as the desktop browser pane's preview or a simulator the user has not yet allowed. When the stack or the app will not start, the done-condition is recorded as blocked as "Environment failures" says, never checked against a weaker stand-in such as a static styleguide page. Record one evidence line per such done-condition: the route, the viewport when named, what was checked, and a screenshot path if one was taken. Screenshots are evidence when appearance matters; the accessibility snapshot is the cheaper check for text and structure. Do not walk the whole app.

Delegate independent investigation to the `bosun-scout` agent in the background with a self-contained prompt, and keep working while it runs. Collect its result when you need it, not before.

Phrase code questions to avoid safeguard false positives: ask "are there any bugs in this program" rather than "does this compile without errors"; give the model documentation for lesser-known languages; keep base64-encoded data out of tool output. If a step still returns a refusal, rephrase it once along those lines. If it persists, record the blocked step in the spec and continue with the other done-conditions.

## Finishing

Before reporting anything non-trivial as done, check the diff against the spec's "Recurring verify failures" lesson, then run `/bosun-verify` and act on its verdict. After two FAILs on the same finding, stop and report both positions to the user instead of looping, unless `Decisions: take recommendations` lets the lead decide it (see Decisions).

What blocks. A verify FAILs a slice only for an unmet done-condition, a failing check, or a release-blocking defect (below) with evidence that it can happen: a concrete input or path the app actually accepts, cited from the code or shown by a command. A defect only an input the app never accepts could reach is not a finding. Reachable defects that are not release-blocking (release-blocking means security, lost or wrong data, wrong money, or a broken core flow) make PASS WITH FOLLOW-UPS. A nit is reported only when it is in the slice's own diff, under its own heading; the lead fixes it before committing or it is dropped, and no nit, found by a verifier or noticed while working, is written down as a follow-up.

The verify limit. A slice gets at most three verify runs, counting every FAIL and every re-verify after PASS WITH FOLLOW-UPS, whether the findings repeat or not; a rerun because a check could not run (below) does not count. When the third is PASS WITH FOLLOW-UPS, the slice ships, and any non-blocking bug in its own work becomes a `bug` follow-up instead of a fourth round. When the third is a FAIL, the slice stops there: the work stays in its worktree, the open findings go to the user with the lead's position on each (from a lane, to the hub), and the run stops as for two FAILs on the same finding. The limit covers a slice up to its PR; a later fix to that PR ("Merge flow") is verified with its own limit of three.

A verify that could not run a check it was asked to run, for example because no stack was free or the machine was too loaded for a build or a browser check, reports those done-conditions as not verified, never as met. The lead reruns that verify once the machine allows, or records the step as blocked as "Environment failures" says; it never reports the slice verified on a reduced check. The verifier re-checks route-or-screen done-conditions in its own browser, or in its own simulator when the brief says `Surface: ios`, following your evidence lines. Report the outcome first, tie every claim to a tool result from this session, and list follow-ups separately from the delivered work. If stopping mid-slice, run `/bosun-checkpoint`.
