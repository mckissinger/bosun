# Bosun brief

The lead runs long tasks well when the goal is clear and stops to ask when it is not. This skill makes the goal clear once, in the spec, so runs need no mid-task input.

## Find the spec

Look for `SPEC.md` at the repo root, then under the repo's docs convention. If none exists, follow "No spec yet". Otherwise follow "Spec exists".

## Model

Bosun runs on Opus 5.5 in every role (core rules, "Model"): you brief, implement directly, keep the spec, commit, and fix FAIL findings yourself, with the project-local `bosun-scout` and a fresh read-only verifier. Before briefing or running, confirm the session model is `claude-opus-5-5`; a spec line does not switch it. If it differs, switch with `/model claude-opus-5-5` or relaunch with `claude --model claude-opus-5-5`, and confirm before continuing. Run `/bosun-mode opus` when the local scout and verifier definitions are absent, and restart Claude Code if that creates the project's first `.claude/agents/` directory. Never fall back to plugin-scoped agents.

If the spec's `Provider mode:` line names anything but `opus` (`fable` and `fable-opus` were removed in 0.24.0; `codex`, `fable-crew`, `astra-crew` and `astra` in 0.18.0), report the value, say it was removed, say to change the line to `Provider mode: opus` or delete it, and stop without briefing or running anything.

## Find the run policy

A line `Run policy: until blocked` or `Run policy: until blocked, max N slices` anywhere in the spec makes this a continuous run: after each slice verifies, the next one starts in the same turn, as described in "Until blocked" below. Anything else (including no line) is `one slice`: brief, run, verify, report, stop. `until blocked` without a `max` means `max 10 slices`.

## Find the decisions and design settings

A line `Decisions: take recommendations` anywhere in the spec lets the lead decide open questions itself and keep running; anything else (including no line) is `ask`. A line `Design approval: me` or `Design approval: critique` sets who approves a new screen's mockup; a project with UI and no line is `me`. The core rules' "Decisions" and "Design" sections hold what each value allows.

## No spec yet: create it and stop

1. Gather. Read the request and everything the user supplied: pasted structures, document paths, existing code. Batch the reads. If the directory has no git repository, initialize one. If the repo has a docs convention, the spec goes there; otherwise `SPEC.md` at the root. Say which path you chose.
2. Write the spec. It must contain, findably: the outcome; the user's decisions in their own words; every done-condition you can state so that a read-only verifier could check it with git diff, file reads, and the repo's checks (anything only a person can confirm is marked human-check); an undecided list holding everything you could not settle, stated as questions, not guesses; an out-of-scope list; a current-slice section, a slice log and a follow-ups section, each holding one line pointing to the `slices/` folder of slice records (core rules, "Slice records"); and an empty lessons section. If the user asked for continuous runs, add `Run policy: until blocked, max N slices` under the first heading; otherwise leave that line out. Choose the layout for this project. Keep it reviewable in one sitting.
3. Stop. End the turn asking the user to review the spec, answer or edit the undecided items they can, and say go. Do not build yet. This is the one planned stop in the workflow.

## Spec exists: brief a slice and run

1. Read the spec, including its lessons, and the open slice records. Under `Decisions: take recommendations`, first decide each undecided item the core rules' "Decisions" section lets you decide (one the spec's outcome or decisions point to, and not on the never-decide list), record it as that section says, and move it out of the undecided list; then judge what is runnable. If no runnable done-condition remains (status `todo` or `in progress`, not `human-check`, nothing it needs on the undecided list), follow "Exhausted roadmap" below and stop. Otherwise take the done-conditions the user named, or the next unstarted ones that form a coherent slice. Undecided items are out of scope for this slice.
2. Gather what the slice depends on: the files involved, the test setup, the exact check commands and any setup they need, and the branch state. Batch the reads. Hand side questions to `bosun-scout` in the background and keep working.
3. Write the slice brief into the slice's record, `slices/<date>-<slice-name>.md` beside the spec (core rules, "Slice records"; add the folder and the spec's three pointer lines if this is the project's first record), and in your reply:

```
Outcome: <one sentence>
Done-conditions: <numbered; each checkable by the verifier's tools, or marked human-check>
Size: <estimated changed lines of source and tests; over about 400, the parts it is split into and which this slice is (core rules, "Slice size"), or the reason a mechanical change exceeds it>
Surface: ios  (include only when a done-condition names a native screen)
Out of scope: <what a careful engineer might touch but must not>
Assumptions: <each ambiguity and the reading chosen, with why>
Decisions: <ask | take recommendations, and its source: the spec line, or the default>
Design approval: <me | critique, and its source: the spec line, or the default; include only when a done-condition adds or changes a screen>
Design: <include only when a done-condition adds or changes a screen: the design skill to load, the locked-rules file, and for each screen its approved board (file, page and board name) and any departures already approved; "no board yet" for a screen to mock up first>
Effort assumed: <the session's level; you cannot change it>
Verifier effort: <this slice's override, project default, or high; independent of the lead's effort>
Checks: <exact commands and any setup they need; end-to-end checks name the targeted specs, not the full suite, and say whether a required CI check runs the full end-to-end suite>
Branch: <name>
```

   For a small task, one line each for outcome, done-condition, and check is the whole brief. Resolve verifier effort as `/bosun-verify` specifies; the brief records the effective value and its source. Do not carry a previous slice's override into a new slice.

4. Branch. Start from the latest default branch (`git fetch` first). If this slice depends on an unmerged slice, build it only after that slice merges: under `until blocked`, take independent work meanwhile or wait, as the core rules' "Merge flow" says; under `one slice`, do not start it, and report which PR it waits for. While another slice's PR is open, work in a new worktree for this slice. Never stack on an unmerged branch, and never work on the default branch.
5. Decide whether to stop. Under `Decisions: ask`, end the turn only if a decision that only the user can make blocks the slice and any assumption would make the work useless or unsafe. Under `Decisions: take recommendations`, decide open questions yourself and record each as the core rules' "Decisions" section says; when part of the slice needs a decision on that section's never-decide list, park it there and take the other runnable work, ending the turn only when no runnable work is left. Otherwise state the assumptions and continue in the same turn.
6. Execute. Work through the done-conditions and update each one's status as it lands, where it lives (the spec for a roadmap done-condition, the record for one this brief defines). Follow the scope, edit, and Tests and CI rules in the core rules. If the diff passes about 400 changed lines of source and tests before the done-conditions are met, stop adding, finish the part that stands on its own, and move the rest into the next part's brief (core rules, "Slice size"). If a done-condition names a route or web screen, run the app and check it with the browser tool this session has (the desktop browser pane, or Playwright MCP) before marking it done, using headless Playwright only in a lane or any session no one is watching, never a tool that waits on an approval prompt, and recording the done-condition as blocked when the stack or app will not start rather than checking a weaker stand-in (core rules, "While working"); a route-or-screen done-condition may name a viewport width, and its evidence line must then carry the viewport so the verifier can re-check it in Playwright at that width. Record in the slice's record the route, the viewport when named, what was checked, and a screenshot path if one was taken. If a done-condition names a native screen, set `Surface: ios`, check it before marking it done with the simulator tool this session has or with `xcrun simctl` from the shell when it has none (in a lane or any session no one is watching, never with a tool that waits on an approval prompt), and record the evidence line as: screen, device, what was checked, screenshot path. If a done-condition adds or changes a screen, run the core rules' "Design" loop for it under the brief's `Design approval:` value, and put its screenshot paths and the paths of the board images exported in this slice in the evidence lines. Do not end the turn to announce a next step; do the step.
7. Verify. First check the slice's diff against each kind of defect in the spec's "Recurring verify failures" lesson and fix what you find, then commit the slice's work and run the self-check on that commit (core rules, "Finishing"). Then run `/bosun-verify` and act on its verdict; every run after the first is a delta re-check of the fix, and after PASS WITH FOLLOW-UPS only a reachable bug or security issue in the slice's own work gets one (core rules, "Delta re-checks"), within the core rules' verify limit of three runs per slice ("Finishing"). After two FAILs on the same finding, stop and report both positions; under `Decisions: take recommendations`, decide it instead as the core rules' "Decisions" section says (record the decision, take the fix you recommend, verify again), and stop at a third FAIL on the same finding.
8. Record lessons. Before reporting, add to the spec's lessons section anything this slice taught that a fresh session would need and the repo does not record, following the lessons rules in the core rules. Correct or delete entries this slice proved wrong. Often there is nothing to add.
9. Report. Outcome first, then each done-condition with its evidence, then an `Evidence:` list of the route-or-screen checks (route or screen, viewport or device when applicable, what was checked, screenshot path, and the board-export paths for a screen with a board), then follow-ups you noticed but did not do, then anything left out and why. Write the slice's `Log:` line in its record: date, slice name, first-verify verdict, the kind of each blocking finding in a few words (for example "another account's rows readable"), so triage can keep the "Recurring verify failures" lesson, and how many done-conditions named a route or screen against how many the verifier confirmed in its browser or simulator. Add each follow-up to the record's Follow-ups section, one line with the slice name, the date, and its tag (`bug`, `drift`, or `deferral`; nits are never written down, as the core rules' "Finishing" says). If undecided items remain, you may add draft done-conditions for the next one to the spec, clearly marked as drafts for the user. If you are stopping mid-slice, run `/bosun-checkpoint`. Under `until blocked`, for a slice that verified PASS or PASS WITH FOLLOW-UPS, make this step's record and spec writes (the `Log:` line, follow-ups, drafts) first, so they are in the slice's commit; then commit, push and open the PR as "Until blocked" says, and write the report after that, so it names the PR. Do not end the turn after it; continue with "Until blocked".

## Until blocked

Under `Run policy: until blocked`, after step 8 and step 9's record and spec writes, for a slice that verified PASS or PASS WITH FOLLOW-UPS: commit, push the branch, open a PR for it with `gh pr create` (summary, verification, follow-ups), arm auto-merge as the core rules' "Run policy" section says (`gh pr merge <n> --auto --merge`; `gh pr merge <n> --merge` only when GitHub refuses because every required check is already green; never past a red or missing required check; leave the PR open and say so when the repo has no required checks or disallows auto-merge, or when the spec or the user's instructions say merging is the user's), then write step 9's report and go back to step 1 for the next slice in the same turn. Do not idle on the PR's CI (wait only where the core rules' "Merge flow" says), and do not end the turn to ask whether to continue or to announce the next slice; only the stop list below ends the run. Each slice gets its own branch from the latest default branch (step 4) and its own PR. A change that touches only records (spec, docs, design boards) gets no PR of its own: it rides on the slice in flight or the next one, as the core rules' "Records ride along" says. Before starting each slice, after each verify, and while waiting, check the run's open PRs and the latest run of every workflow on the default branch, and act on them as the core rules' "Merge flow" says: fix a red or conflicting PR, or one the merge queue removed (by its reason, as the core rules' "Queue removal" says, never re-armed after failed checks without reading the failed run, and a removal a person made only reported), verifying a code fix, before going on, except `bosun-ci`'s throwaway selection-proof PR, which is closed unmerged once its check reports, fix a red default branch first (a flake candidate, an environment failure, or a red run of a workflow that only reports is reported instead), and, where the repo requires up-to-date branches without a merge queue, update the oldest behind PR. Every slice, including one built while another of the run's PRs is open, writes its brief in its own record. Keep a count of slices started in this run, including the first. At the start of the run and at each milestone end, check whether lanes apply ("Lanes" below).

At each milestone end (core rules, "Follow-ups and milestones": a group of done-conditions the spec names as one, or every fifth slice when it names none), run `/bosun-triage` (which also finds merged, clean, idle worktrees and branches and removes them when applied; see its "Git cleanup"), then a hygiene slice with its own PR for the open bugs, then a `/bosun-ci` audit against recent runs, reading the latest weekly CI report where the project posts one, whose findings become follow-ups and whose fixes run as their own slice. When more than five bugs are open, make the next slice a hygiene slice.

Stop, and say in the report which condition stopped the run, at the first of:

- no runnable done-condition remains ("Exhausted roadmap");
- every remaining runnable item needs a decision the lead may not make (core rules, "Decisions");
- a verify produced two FAILs on the same finding, or three under `Decisions: take recommendations` (step 7);
- a slice's third verify run was a FAIL (the core rules' verify limit, "Finishing");
- every remaining runnable slice waits on an unmerged PR that cannot merge on its own (core rules, "Merge flow");
- an environment failure blocks every remaining runnable slice (core rules, "Environment failures");
- the count has reached `max N`.

A hub whose lanes are running and that has no planning work left pauses instead ("Lanes"); that does not end the run.

## Lanes

The core rules' "Lanes" section says when lanes run and what binds them. This is the procedure.

As the hub, at the start of an `until blocked` run and at each milestone end:

1. Choose the shape (core rules, "Shapes"). With fewer than five runnable slices, when the user has said they won't be steering, or when another condition fails, run as one session and say nothing more about lanes. Otherwise group the runnable done-conditions into areas by the files and tables they touch: two independent areas of at least three slices each make two lanes, and anything else makes one lane that takes all the work. Shared test stacks with no `Stack isolation:` line do not fail the check; they add the setup slice (step 3).
2. Propose. Name the shape, each area and the slices it holds, the shared files, each lane's declaration (the files and directories, tables, and shared contracts its slices plan to touch; core rules, "Declarations"), any shared contract that lands first as its own slice, each lane's slice cap (together with the slices already built, within `max N`), the stack each lane will claim, and what is likely to need the user. Under either `Decisions:` value, start lanes only on the user's yes. The proposal is not a stop: state it in the run's first slice report and again at each milestone end until the user answers, and run as one session meanwhile. A yes covers the rest of the run; a no stands until the next run.
3. After the yes, finish the slice you are on. If the setup slice is needed (core rules, "Stack isolation"), run it next as an ordinary slice, and run any shared-contract slice the proposal named the same way. Never start two lanes whose declarations overlap. It verifies its isolation by running one lane's checks while the main stack stays untouched, compared before and after. Start lanes once its PR merges. While lanes run, write no code.
4. Set each lane's cap so the slices already started plus every lane's cap stay within `max N`. Start each lane with the app's start-session tool: a fresh context, its own worktree, the hub woken when the lane finishes, and, where the tool can set them, the model (`claude-opus-5-5`) and the hub's effort. The prompt follows this template:

```
You are Lane <X> of a Bosun run on <repo> with <one|two> lane(s). The hub (the session that started you) plans, decides with the user and keeps the spec; it does not build. Every code change in this run is made by a lane.
Your area: <spec rows or done-conditions>, in this order: <...>. Work only your area and slices the hub assigns you; send anything else to the hub.
Start: read the project instructions, the spec (decisions, undecided, lessons) and the slice records (open ones, and recent ones for format). Then run /bosun-brief for your first slice and continue under the spec's run policy, decisions and design settings, with your own cap: max <M> slices.
Each slice: its own branch from the latest origin/<default>, its own PR with auto-merge as the core rules' "Run policy" says, a fresh verifier before the PR. Never stack on an unmerged branch. Watch and fix your own PRs, except a `bosun-ci` selection-proof PR, which you close unmerged once its check reports. After opening a PR that merges on its own, your last one included, never end your turn saying you are waiting on CI unless a background wait or the host's PR monitor will wake you when it merges, a check fails, it conflicts, the merge queue removes it, or it is green but neither merged nor queued; then act on whichever happened (a queue removal by its reason, as the core rules' "Queue removal" says, never re-arming auto-merge after failed checks without reading the failed run, and only reporting a removal a person made), and start a split slice's next part when the previous part merges (core rules, "Following a PR"). Decide only undecided items in your area; send others to the hub. Skip milestone-end work (triage, CI audit); the hub does it. A hygiene slice of your own counts only bugs in your area.
Assigned slices: the hub may assign you a shared-file change, a fix for a red default branch, a hygiene slice or a CI fix. Take it next, after the slice you are on. If you see the default branch red, tell the hub and do not fix it unless the hub assigns it to you; finish your current slice and keep working your area.
Model: confirm your session model is claude-opus-5-5 before the first slice; if it is not, report that to the hub and stop.
Stack: claim lane <K> with `<stack isolation command>` before any migration, end-to-end test, seed or data-resetting suite, run them only through it, and tell every verifier to do the same. Never touch the main stack or its ports. Remove it with the command's teardown when you finish.
Paths: every screenshot and output path, yours and your verifiers', is absolute and inside your worktree.
Screens: check routes with headless Playwright only; never use the desktop browser pane, a preview tool or anything else that waits on an approval prompt. If the stack or app will not start, record the done-condition as blocked and tell the hub; never check a weaker stand-in.
Your declaration (files and directories, tables, shared contracts): <list>. Before touching anything outside it, ask the hub, and wait for its answer; take other work in your area meanwhile.
Shared files (edit only in a slice the hub assigns you; otherwise message the hub): <list>. If the hub tells you another lane holds some of your area's files for an assigned slice, leave them alone until that slice merges.
Protected paths and decisions that need the user: <list>. When you reach one, record it in the slice, send the hub one short message (what, why, where the screenshots are), and take other runnable work. Wherever Bosun says to ask, stop for or report to the user, send it to the hub instead. Do not ask the user directly.
Spec: write each slice's brief, evidence, verify verdicts, `Log:` line and follow-ups in its own record, `slices/<date>-<slice-name>.md` beside the spec, and in the spec only what the core rules' "Slice records" leaves there: statuses of roadmap done-conditions, lessons, and any decision you take under the spec's `Decisions:` setting (with its undecided item moved), draft done-conditions and blocked steps; when the hub sends you a decision, write it into the spec on your current slice's branch, in the user's words as quoted; on a merge conflict in the spec, keep both sides. Records-only changes never get a PR of their own; they ride on your next slice, and on your last slice, send any left over to the hub.
Done: your area and assigned slices are done, you reach the cap, or the run policy's stop list stops you. Then remove your stack with the command's teardown and, once each of your PRs has merged or closed or cannot merge on its own (a PR parked on a red check you have stopped fixing, at the verify limit or after an environment failure's one rerun, counts as one that cannot), report to the hub: why you stopped, each slice, PR, verify verdicts, follow-ups, and everything waiting on the user.
```

While lanes run, the hub plans and does not build:

- It answers lane messages and brings the user's items to the user, batched.
- It reviews finished screens with the user beside their boards.
- It sends each decision taken with the user, and each change to the undecided or out-of-scope lists, to the lane whose area it touches, quoting the user's words, and that lane records it on its slice branch; when two lanes need one, it names one to record it. Everything else it records on one records branch, its own log entries included (production pushes, refunds, approvals), pushing it after each entry; that branch's PR opens once per milestone end, at the run's end, or when the user asks, with auto-merge, and no log entry gets a PR of its own. It plans the next work.
- It watches the latest run of every workflow on the default branch.
- It assigns code work to lanes as slices at the top of their queues: a shared-file change to one lane at a time (and when two areas each need the same new page or component, it names the one slice that builds it, and the other lane waits for that slice to merge), a red default branch's fix to one lane (not a red run of a workflow that only reports, whose findings become follow-ups, except the nightly hunt's flakes where the project runs a flake-fix loop, which are the loop's), and milestone hygiene and CI-audit fixes to the lane whose area holds the files (work spanning both areas or touching shared files to one lane, telling the other lane which of its files are held).
- At a milestone end (a named group done, or every fifth slice merged across the run) it runs `/bosun-triage` and the `/bosun-ci` audit, reading the latest weekly CI report where the project posts one; their code work goes to lanes.
- It never forwards a lane's request as the user's approval, and quotes the user's own words when relaying an answer.
- When a lane reports, it reads that lane's PRs and their checks before reporting them done, and removes anything a lane left outside its worktree only after checking what it is. Once the lane has reported and its PRs have merged or closed, it archives the lane's session with the host's archive tool where it has one (archive, never delete) and confirms the lane's stack is gone, reporting rather than stopping one still running; a lane waiting on a PR, a verify or a decision stays.
- It judges a lane's progress by its commits, PR state and transcript times, not by a "running" flag.
- With no planning work left, it ends its turn saying which lanes are running. This is a pause; a lane's message, a lane's end or the user wakes it, and the run continues.
- When the last lane ends with runnable work left and the count below `max N`, leaving out work parked on two FAILs on the same finding, at the verify limit, on a user-only item or on an environment failure (those go to the user), it picks the shape again under the same yes: new lanes where the shape allows, otherwise it builds again as one session. Otherwise the run ends at the stop that applies.

In a lane session: follow the prompt as written. Run `/bosun-brief` under the spec's policies with the cap the prompt sets, without milestone-end work, taking assigned slices next. Send the hub, not the user, the user-only items the core rules' "Lanes" section names and anything Bosun would otherwise ask or report to the user. Report to the hub when done or stopped, once each of your PRs has merged or closed or cannot merge on its own.

When the session cannot start other sessions, the hub prints each lane prompt in its proposal so the user can start the lanes by hand after saying yes, and then acts as the hub as above. Hand-started lanes cannot message or wake the hub, so each printed prompt says to put hub messages in the lane's own reports, and the user carries them to the hub.

## Exhausted roadmap

When no runnable done-condition remains, at the start or between slices, under either policy, do not invent work. Under `Decisions: take recommendations`, this applies only after step 1 has decided the undecided items it may decide. Report, in this order: that the roadmap is exhausted; every open human-check condition; every undecided item, as the question the spec records; and candidate next slices drawn from the open follow-ups (the spec's section and the slice records'), each written as a draft done-condition and marked as a proposal. End the turn asking what next. Never promote a proposal into a done-condition yourself; the user says which, if any, become work. The one exception: under `Decisions: take recommendations`, a hygiene slice built from open bug follow-ups is runnable work, so promote those bugs to done-conditions and run it before reporting the roadmap exhausted. New features are still never invented.

## Long deliverables at xhigh or max

If the session runs at `xhigh` or `max` and a step produces a long deliverable (a large file, a long document), keep this in mind before writing it, with the real limit filled in (`CLAUDE_CODE_MAX_OUTPUT_TOKENS` if set, otherwise the model's 128,000 output cap):

> Everything produced in one reply, including any reasoning or drafting it does before the reply, counts toward a single limit of about [max_tokens] tokens. If that limit is reached before the reply is finished, the person receives a cut-off response and has to start over. Composing an entire output or deliverable in full as reasoning and then again as a reply would double the length of the turn without improving the result, so don't do that. Instead, spend extra effort on understanding the request, checking the inputs the answer depends on, settling the structure and other difficult decisions, and otherwise use the reasoning space to reason and the output space to write an output.
