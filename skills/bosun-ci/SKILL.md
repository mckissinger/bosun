# Bosun CI

Shorten time to trustworthy CI results while preserving coverage. V1 supports GitHub Actions. For another provider, explain that limit and offer a provider-specific follow-up; do not rewrite its configuration as GitHub Actions.

## Select the outcome

- **Audit CI**, review, or recommendations: read-only investigation and a ranked report. Do not edit the spec or workflows, launch runs, or invoke the implementation flow. A spec is useful context but not required for an audit.
- **Speed up CI**, optimize, or fix an identified CI bottleneck: investigate, then implement a focused improvement through `/bosun-brief` and verify through `/bosun-verify`. Honor existing authorization; do not insert another approval step when implementation is already requested. The brief's model, spec, and run-policy rules still apply.
- **Turn on a merge queue**, **set up migrations**, **set up the flake-fix loop**, or **set up the weekly CI report**: when the user asks by name, follow that section below, through `/bosun-brief` and `/bosun-verify` for its code.
- If the request does not establish whether to edit, default to audit. Keep deployment changes and repository protection changes, including turning on a merge queue and the migrations flow below, outside a CI performance request unless separately requested. A move to Blacksmith runners is always a recommendation under "Runner standard"; implement it only when the user asked for the migration.

## Establish the baseline

Start with the conformance check below, then read `.github/workflows/`, referenced reusable workflows and local actions, package/build configuration, and the actual check commands. Inspect remote reusable workflows at the referenced revision when accessible. Map triggers, matrix variants, `needs` dependencies, conditions, required checks, permissions, and shared artifacts before proposing removals or skipped work. If protection settings or referenced code are inaccessible, state what is unknown.

Read the default branch's merge setup with `gh api`, from both classic branch protection and rulesets (`repos/{owner}/{repo}/rules/branches/{branch}` lists every rule that applies to the branch): required checks, whether branches must be up to date before merging, and whether a merge queue is on. A 404 from the classic `branches/{branch}/protection` endpoint means only that the branch has no classic protection; call the branch unprotected only when the rulesets list nothing for it either. Requiring up-to-date branches without a merge queue is a finding, because each merge leaves the other open PRs behind and auto-merge does not update them (core rules, "Merge flow"); recommend a merge queue where GitHub offers one, and otherwise turning the requirement off with CI on pushes to the default branch. Under a merge queue, a required workflow without a `merge_group` trigger never reports, so queued PRs hang, and a job that reads a PR number (such as a changed-files gate on `pulls/{n}/files`) with no `merge_group` fallback that runs everything fails or skips in the queue: report either as a blocking finding. The one exception is a check that only makes sense on a PR's diff and reports success in the queue, as "Turning on a merge queue" describes. A repository in a personal account, or a private organization repository without GitHub Enterprise Cloud, cannot have a queue: say so, and leave any move or plan change to the user.

Use available authenticated GitHub tooling or the user's exported run data. With `gh`, useful read-only entry points are `gh run list`, `gh run view <run-id>`, and the Actions jobs API for job/step timestamps. Consult current official GitHub documentation for API fields, workflow syntax, and action versions before changing them. Paginate job listings so large matrices are not silently truncated; identify run attempts when examining reruns. Never print credentials or indiscriminately dump logs that may contain secrets.

Choose a bounded sample of recent, comparable completed runs; aim for several observations rather than treating one fast run as typical. Record workflow, commit, event, branch, runner type, matrix, run attempt, conclusion, and run URL. Separate successful runs from failed, cancelled, and rerun attempts. Missing access or history still permits a static audit; mark its findings as hypotheses and performance as unmeasured.

Separate these quantities where the data supports them:

- **Elapsed time:** the last attempt's start to the required CI checks completing. State the exact interval measured and any omitted scheduling delay. With multiple required workflows, use their combined completion boundary, not only the fastest workflow. Use the run's last attempt: its start (the attempt's `run_started_at`) to the last required job's `completed_at` (the Actions jobs API), with the wait before the first job started reported as queue time, and report earlier attempts separately; a run's `created_at` to `updated_at` also counts the wait before a rerun and any later update to the run, so it inflates the tail and hides which job is slow.
- **Queue and execution:** distinguish runner waiting from dependency waiting and work on a runner. If timestamps cannot separate them, report the combined delay without attributing a cause.
- **Runner minutes:** sum job execution durations, including matrix jobs and retries. This is compute use, not a dollar-cost estimate; pricing and runner multipliers need separate evidence.
- **Step time:** setup/install, build, tests, artifact/cache transfer, and other dominant work. Follow the dependency chain that actually determines completion; parallel job durations do not add up to elapsed time.
- **Reliability:** identify repeat failures and retries with evidence. A failure that passes on rerun is a flake candidate, not proof; check for code and environment changes.
- **Runs per merged PR:** for PRs merged in the sample window, count the PR's CI runs, its distinct head commits (pushes), and its catch-up runs: runs whose head commit is a merge whose second parent is on the default branch, which is what GitHub's Update branch and `gh pr update-branch` create. A rebase onto the default branch cannot be told apart from an ordinary force-push from run data, so report those as unknown rather than as catch-up or not. A large catch-up share, by runs or by runner minutes, is a finding: it is the cost of requiring up-to-date branches without a merge queue, and it grows faster than the merge rate, since more merges leave more open PRs behind more often. Report it with the up-to-date-branches finding above where that applies; under a merge queue, catch-up runs mean something still updates branches by hand.
- **Merge-path latency:** for each merged PR, the time from the last required check completing on its final head commit to `merged_at`, as a median and, when the sample supports it, a p95. Under a merge queue this includes the queue's own run; say so rather than subtracting it. Once PR checks are fast, this wait (a person or tool noticing the PR is ready, the queue, an update from the default branch) is often the larger share of time to merge.
- **Cache health** (read only): total usage from `gh api repos/{owner}/{repo}/actions/cache/usage` against the repository's cache limit (10 GB by default; past it, the least recently used entries are evicted and later restores miss); hit or miss per job, from each cache restore step's log; whether the entries PRs restore were saved from the default branch (the cache list's `ref`, or the provider's own cache view where GitHub's list reads empty), since a PR can restore the default branch's caches but not another PR's, so with no default-branch entry every new PR starts cold; and each cache's restore time against the step it replaces. Runners that send `actions/cache` to their own store (Blacksmith does) leave GitHub's usage API and cache list empty: read usage from the provider where it can be read, take hits from the restore steps' logs or from the steps a hit skips, and never report an empty API or list as a healthy cache, nor as proof that no default-branch entry exists. A cache that misses fails nothing, so report each of these that shows a problem as a finding; fixes go through "Choose a change".
- **Selection proof:** for each change-based selection or path gate on a required check, whether a real change it should cover has ever been shown to turn that check red (see "Implement through Bosun"). A gate with no such proof is a finding, because a selection miss reports green. The audit records this from the gate's history and PRs; it does not launch a run to test it.
- **Repeat push runs:** under a merge queue, count push runs on the default branch whose head commit already passed a `merge_group` run of the same workflow, and their share of runner minutes. The queue moves the default branch to the commit it tested, so these runs re-prove a result already in hand; a large share is a finding, with the fix under "Choose a change".
- **Flake-hunt coverage:** list each test suite a required check runs (unit, database, end-to-end and any other) and whether the nightly flake hunt repeats it. A suite outside the hunt is a finding, more so when it is among the jobs failing in the merge queue or failing on a PR and then passing with no new commit, since its flakes then cost re-queues and reruns that nothing ever counts or fixes.

Record sample size, typical duration (median when meaningful), spread, and warm/cold/unknown cache state. Do not infer a cache hit from a fast install alone. Use tail percentiles only when the sample supports them.

Where the project posts a weekly CI report, read the latest one for trends the sample may not show. Compare the results with the spec's `CI budget:` line, the user's target for PR CI (for example `CI budget: PR checks 10 min median`). A median over the budget is a finding, and so is a job whose median grew by half or more over the last two weeks, since suites that grow quietly reach the critical path before anyone looks. With no line, propose a budget from the measured medians and leave the value to the user; the lead never sets it.

## Conformance check

`python3 "<plugin root>/scripts/ci-conformance.py" --repo-dir <checkout>` checks a repository against this skill's standard, whatever its stack, from its workflow files, its test-runner retry settings and the default branch's merge setup (read through `gh`; `--offline` skips the settings and reports them unknown). Resolve the plugin root from this skill's location. Run it on a checkout of the default branch, not a stale or feature branch. It reports each finding as FAIL, WARN or INFO and exits 1 on any FAIL:

- **FAIL:** up-to-date branches required without a merge queue; a required check whose workflow lacks a `pull_request` trigger, or under a queue a `merge_group` trigger; end-to-end or unit retries above one; under a queue, a push-run skip whose lookup job lacks `actions: read` or job-level `continue-on-error`, or a job anywhere behind it (directly or through other jobs) whose `if:` has none of `!cancelled()`, `always()` or `failure()`.
- **WARN:** no merge queue (INFO for a personal repository, which cannot have one); a required check that maps to no workflow job (often an app's check); jobs off Blacksmith in an organization repository (INFO for a personal repository or an unknown owner); no change-based selection on a PR workflow; under a queue, push runs on the default branch with no repeat-run skip; no scheduled flake hunt that repeats tests; a PR workflow without `concurrency` cancellation; no `CI budget:` line in the spec.

Its detections of selection, the push-run skip and the flake hunt read workflow text, so a WARN there can be a false alarm (for example a diff-only check such as a security review has nothing to select), and a required check posted by a reusable workflow (`caller / job`) or an app maps to no job: confirm it in the workflow before acting. The audit runs the check first and lists its findings with the others. Every CI improvement slice ends with the check reporting no FAIL and each remaining WARN either fixed or justified in the spec. Two kinds of FAIL may stay, each recorded in the spec with why and what clears it: retries above one while "Flaky checks" holds them until the hunt shows their flakes fixed or quarantined, and a FAIL whose fix is a repository protection change (such as the up-to-date requirement), which "Select the outcome" leaves to a separate request. The weekly report includes its result, so drift between projects shows up without anyone looking.

## Runner standard

Blacksmith runners are the standard for GitHub Actions. A job on a GitHub-hosted runner is a finding: recommend its Blacksmith equivalent (for example, `ubuntu-latest` becomes a 2 vCPU Ubuntu Blacksmith runner) and size each job from its measured duration and resource use, with small checks on 2 vCPU and builds and heavy test shards on 4 to 8. Confirm runner labels, sizes, and cache actions against Blacksmith's current documentation before writing them; use its co-located cache actions where its migration tooling adds them. Blacksmith works only for repositories in a GitHub organization whose Default runner group includes the repository; for a personal repository, say that instead of recommending it.

Recommend routing each class of job's `runs-on` through one repository variable with a literal fallback (for example `runs-on: ${{ vars.RUNNER_SMALL || '<current label>' }}`), so moving a class of jobs to another runner, or back after a provider's capacity limit or outage, is a one-line change. Like the Blacksmith move, it is a recommendation, implemented only when the user asks; confirm the expression syntax against current GitHub documentation before writing it.

Faster runners can introduce new failure modes. After a migration, compare checkout duration with the baseline and look for hung or retried checkouts. Linear saw checkout slow down and occasionally hang after leaving GitHub-hosted runners, from the network between the new runners and GitHub, and fixed it with retry-with-backoff, low-speed git timeouts, and cached git mirrors.

## Turning on a merge queue

Do this when the user asked for it, one repository at a time. A queue earns its cost where PRs pile up, or where affected-only tests need a required full run before merge. Each queued PR runs the full required checks on top of the entries ahead of it, so a repository with little PR traffic can wait.

1. **Workflows first, in an ordinary PR.** Every required check's workflow triggers on `merge_group`, and any job that reads a PR number or diff gets a fallback that runs everything. A required check that only makes sense on a PR's diff, such as a security review, reports success on `merge_group`, because a PR enters the queue only after its own required checks pass; state that in the coverage justification. A queue also refuses direct pushes to the default branch, even from admins, so anything that pushes there (release scripts, bots, workflows) moves to opening PRs first.
2. **Merge that PR,** then confirm the trigger is on the default branch. Turning the queue on before this leaves queued PRs waiting on a check that never arrives.
3. **Turn the queue on.** Create a ruleset for the default branch with a `merge_queue` rule (`POST repos/{owner}/{repo}/rulesets`, repository admin), or have an admin tick Require merge queue in classic branch protection. A ruleset's queue works alongside classic protection that holds the required checks. Starting values, to adjust from measured runs (a classic setup may offer fewer of them, which step 4's read-back shows):
   - merge method: the one the project merges with, such as `MERGE` for merge commits (the queue sets it, and `gh pr merge --auto --merge` only notes that);
   - grouping: all entries must pass (`ALLGREEN`);
   - minimum group 1, maximum group 5, wait 5 minutes;
   - build concurrency 2 where each entry's full suite is expensive, raised only after measuring;
   - check timeout above the full run's slowest recent time, with room for retries.
4. **Prove it with one low-risk PR.** Confirm a `merge_group` run reports every required check, the PR merges, and the configuration reads back through GraphQL (`mergeQueue(branch:) { configuration { ... } }`, which reports times in seconds where the ruleset takes minutes). Record the real settings where the project keeps its CI notes, read back rather than remembered.

To undo it, remove the rule or untick the setting; the `merge_group` trigger is harmless on its own. If a path gate relies on the queue's full run, restore full runs on PRs first, or selection misses land on the default branch.

## Choose a change

Rank opportunities by evidence, expected elapsed-time or runner-minute benefit, implementation effort, and coverage risk. Look at the critical path first: a gate job that other jobs `needs` delays every job waiting behind it, so a few seconds there can shorten elapsed time more than larger savings elsewhere. Setup often outweighs test execution; when the baseline shows that, cut setup before adding parallelism. Explain the tradeoff if parallelism reduces elapsed time but increases compute. Do not promise a percentage from workflow inspection alone.

Investigate only candidates supported by the bottleneck, for example:

- Dependency/build caches: confirm hit rates, invalidation inputs, and restore/save overhead, and compare restore time with a fresh filtered install; a cache keyed on a frequently changing lockfile can be slower than reinstalling. Preserve correctness on a cold cache; caches must not be the only way required outputs arrive.
- Repeated builds: build once and pass revision-matched artifacts to consumers where environments and configurations are compatible.
- Identical-input reruns: skip a task whose inputs match a run that already passed, through a task or remote cache keyed on those inputs, so a rebase or re-verify reruns only what changed. It is safe only for hermetic tasks: the key must cover every input the task reads, including environment variables and tool versions. Leave uncached any task that reaches live services, reads the clock, or has shown flakes, since its result can change with identical inputs and cached passes hide the reruns that flake evidence depends on.
- Gate jobs: a shallow or sparse fetch for change detection, no checkout in jobs that do not read the tree, and cache writes or housekeeping moved to a job nothing waits on.
- Repeated setup: a base image for stable system dependencies (which also removes downloads that can hang), installs filtered to the package a job needs rather than the whole workspace, and a generated schema snapshot instead of replaying every migration.
- Playwright's OS packages: `playwright install --with-deps` goes through the runner's apt mirror, which can crawl and can fail a required check for reasons unrelated to the code. On Blacksmith, point apt at `archive.ubuntu.com` before any apt install, in `/etc/apt/apt-mirrors.txt` and `ubuntu.sources` (editing `sources.list` alone does nothing). Where it is still slow, cache the `.deb` files: remove apt's `docker-clean` config, copy the cache into `/var/cache/apt/archives` before installing, and save it from one shard only when new files appeared. Mark the cache steps `continue-on-error`, so a cache problem never fails a shard and a cold cache behaves as before.
- Small checks: batch lint, format, typecheck, and audit into one or two jobs that run them concurrently, grouped by cost, keeping per-task output so a failure still names its script.
- Tooling: a native typechecker where the project's TypeScript supports it (`tsgo`), and lint rules that do not need type information unless they must.
- Job ordering: remove unnecessary `needs` dependencies, starting with a job that `needs` another whose outputs or artifacts it never reads, such as test shards that all wait for a build only one of them restores. Split such a matrix so only its consumers wait.
- Setup hangs: a step-level `timeout-minutes` on each setup step that downloads (toolchain setup, dependency installs, browser and image pulls), set above its slowest recent time, so a hung download fails in minutes instead of holding the job to its own timeout.
- Local service stacks: start a stack the tests need (such as a local Supabase) in the background while dependencies install, and wait for it just before the first test; pre-pull or cache its images, and exclude services no test uses. Check that each image the workflow pre-pulls is one the stack actually starts.
- Database suites: a database or integration suite that sets the floor for every run, including runs with no end-to-end work, is split across runners like any other shard, after its per-runner setup is short.
- Test sharding, only after per-shard setup is short: multiply setup time by the shard count before adding shards, balance with observed timings, and split oversized test files, since runners such as Vitest balance by file rather than by test duration. Judge a balancing or runner-size change on a real run against recent medians rather than its prediction, keep it only for a clear gain, and record what was tried and not adopted, with its numbers, in the spec so it is not tried again.
- Test isolation: letting test files share a module registry (Vitest `isolate: false`) through an explicit per-file opt-in with teardown for shared state, leaving files with fake timers or tangled shared state in an isolated project. Highest reward and highest correctness risk; never enable it globally.
- Push runs the queue already proved: an early job in the push run looks up a successful `merge_group` run of the same workflow for the same head commit (the Actions runs API filtered by `head_sha` and `event=merge_group`). The lookup job needs `actions: read`; without it every lookup is refused and the saving never happens. It also carries job-level `continue-on-error: true`: a lookup that fails on checkout, setup or a timeout otherwise makes the push run conclude failure even though the tests ran. Every job whose `needs` includes the lookup job is skipped whenever the lookup is skipped, which is every pull request, queue and scheduled run, because a job's implicit `success()` covers its whole `needs` chain; give each such job an explicit `if:` (for example `!cancelled()` together with the lookup's output), testing the skip flag so that an empty output, which is what a skipped or failed lookup leaves, runs everything. Otherwise those jobs never run on a PR: a skipped job reports success to a required check, so tests silently stop running, or an aggregate gate or matrix check fails or never reports. When such a run exists and it scoped no suite down (a queue run that skipped end-to-end for a documentation-only group does not count), the other jobs skip (push runs gate no PR, so no required check waits on them); otherwise, including when the lookup fails, everything runs as before. Any aggregate gate job must count this deliberate skip as success, or the push run goes red. The run must still conclude success, so a migrations deploy triggered by `workflow_run` on CI's push run still fires ("Migrations deploy"): confirm that on one real push run before relying on it. Scheduled runs are unchanged. The coverage justification is the identical commit; say so in the slice.
- Superseded PR runs: scope cancellation to the same PR/workflow where safe; keep release/deployment semantics intact.
- Duplicate triggers, broad matrices, and change-based selection (affected-only tests): justify what becomes conditional and how all affected components and supported environments retain coverage, with a full run for shared or configuration changes and on a schedule. When PRs merge automatically on green, a scheduled or post-merge full run finds a selection miss only after it lands, so anything the PR run skips must still run in a required check before merge, such as the full suite in a merge queue. On the PR run itself, keep end-to-end tests full or path-gated, since the import graph cannot select them. A path gate that stays honest: a script maps changed files to a scope, where documentation and unit tests run no end-to-end tests (the check still reports success, so a required check never hangs), a changed spec runs that spec, a change inside a closed area runs that area's specs, and anything else runs the full suite, including shared code, configuration, dependencies, migrations, test helpers, the workflow and the script itself. A test fails when a mapped area gains an outside importer or a spec naming one of its routes is missing from its list, so the map cannot quietly go stale. The queue and pushes to the default branch run the full suite (except a push run that skips because the queue already proved its commit, above), and the run summary says which scope ran and why.
- Flaky checks: address an evidenced cause rather than increasing retries or turning failures into successes. End-to-end retries in CI are at most one (Playwright `retries: 1`). A test that passes only on a retry is a flake: the run's report lists it and the nightly hunt counts it, so retries never hide it. A higher setting is a finding; lower it once the hunt shows the flakes it was absorbing are fixed or quarantined, so the change does not turn PRs red all at once.
- Flake quarantine, with the user's approval or through a flake-fix loop the user set up (core rules, "Tests and CI"): a flaky test, end-to-end, unit or database, keeps running without blocking while it is fixed. Each quarantined test carries a tag and an entry with its owner, reason, date added, and an expiry at most 14 days out. Blocking runs exclude the tag, and a non-blocking step still runs those tests. A test in a required check fails on an expired or over-long entry, a missing owner or reason, or tags and entries that do not match, counting tags the way the test runner matches them. That test reads today's date on purpose, an exception to the no-wall-clock rule for new tests; say so in the verify prompt. An expired entry therefore blocks PRs until someone fixes the test or renews it with a new reason. Keep the list short, since the extra step adds time to every shard.
- Nightly flake hunt: a scheduled run on the default branch, in its own workflow so it is not read as the default branch's CI, repeats every test in every suite a required check runs, unit and database suites as well as end-to-end (Playwright's `--repeat-each=2`, the runner's own repeat option elsewhere, and a second run of the suite where it has none), quarantined ones included, gates nothing, and posts a table of flaky and failed tests to one standing issue. It says when shard reports are missing, so a broken night does not look clean, and it gives flake candidates the rate evidence a fix needs. The flake-fix loop below acts on its table.

Prefer a small coherent change with a measurable hypothesis. If the evidence shows no worthwhile improvement, report that and stop. Put other candidates in the report; during implementation, record deferred candidates in the spec's follow-ups.

## Migrations deploy (opt-in)

Set this up when the user asks, as its own slice, since it deploys. A workflow applies committed migrations after CI passes on the default branch, on the commit CI tested. The project's spec records its production mode, in the user's words.

Every setup has these guards:

- **Trigger.** The triggering run's event is `push` and its branch is the default branch. A branch-name check alone matches a fork's branch of the same name, and a CI workflow that also runs on a schedule would otherwise fire it. A hand start runs only from the default branch. CI must therefore also run on `push` to the default branch, even under a merge queue, or this workflow silently never fires.
- **Environments.** Each database has its own GitHub Environment holding its secret, with deployment branches limited to the default branch. Mask secrets in anything the job prints.
- **Order.** Where a project has a sandbox, it updates first and production runs only after it succeeds. A failed sandbox stops production.
- **One at a time.** One push per database, never cancelled half-way (`concurrency` with `cancel-in-progress: false`).
- **Dry runs.** A dry run lists pending migrations in the job summary, and a second one after pushing confirms nothing is left. A database ahead of the default branch is a green no-op with a warning that names the versions, and production does not run while sandbox is ahead. Any other dry-run error fails red. Migrations merged out of timestamp order, which parallel branches and lanes cause, make a plain push refuse every later push, so the push includes them (for Supabase, `supabase db push --include-all`), after a dry run with the same flag (`--dry-run --include-all`), which lists them in order.
- **Holds.** A migration that must not ship before a date refuses the whole push, because applying the others around it is an order nobody checked.
- **App and migration order.** The app may deploy on merge while the migration waits for CI, and for approval where that applies, so decide per change. Where the migration needs the app, merge the app first. Where the app needs the migration, plan for the gap, or have the user apply the migration before merging, sandbox first.

Production takes one of two modes:

- **Approval.** Recommended once a project has real users or money. Production's environment has a required reviewer with admin bypass off, runs only when sandbox just took migrations, or with a single database when its own dry run finds pending migrations, or when started by hand, and refuses to push if the environment has no required reviewer. Approving is the user's. A session never approves it, even when its `gh` login is the reviewer, so this rests on the rule rather than a technical block.
- **Automatic.** Only by the user's explicit choice, typically before launch or with no real data, where a bad migration is cheap to undo. Production updates after CI with no approval, and the guards above still apply.

## Flake-fix loop (opt-in)

Set this up when the user asks, one repository at a time, once its nightly flake hunt posts to a standing issue. The hunt finds flakes; this loop fixes them, so they do not pile up behind retries.

- **Where it runs.** A scheduled Claude Code routine, daily after the hunt finishes, signed in as the user with the unmodified `claude` binary. Before relying on it, confirm in one run that the routine can read the standing issue and open PRs with `gh`, and record where it runs and its schedule where the project keeps its CI notes.
- **What it takes.** It reads the hunt's latest table and takes at most three tests: those flaky or failed in every repeat first, then the highest rate. It skips a test with an open loop PR, a test already quarantined (except its own entries near expiry, below), and a test it hands to the user (below). A night whose table says shard reports are missing takes nothing.
- **One slice per test.** Each test gets its own Bosun slice, branch, PR and verify, one after another in the same run. The flaky test is that slice's subject, so the core rule against changing code for an unrelated flake candidate does not apply to it. The slice first reproduces the flake by repeating that test alone on the default branch (Playwright's `--repeat-each=20` with `--retries=0`, or the runner's equivalent); a test that does not reproduce waits for another night's evidence. The brief names the evidenced cause and carries two done-conditions: a stated number of consecutive repeats passing with retries off (`--repeat-each=30 --retries=0` by default, or the runner's equivalent), run after the fix and recorded with the command, and that the fix uses none of the changes below. When the test was quarantined, the fix also removes its tag and entry, so the entry cannot expire later and block every PR. The loop skips a test whose fix would touch a file that any open PR changes (read from GitHub, so a scheduled routine sees what lanes and other sessions hold), and says so in its report.
- **What is not a fix.** Longer timeouts or waits, more retries, sleeps, skipping or tagging the test out of the blocking run, catching the failure, and loosening or deleting an assertion. Because the brief makes "uses none of these" a done-condition, a diff that relies on one fails verify.
- **No cause found.** The loop opens a quarantine PR instead, as its own brief and verify, whose done-conditions are the entry's fields and the quarantine check passing (the fix slice's "uses none of these" does not apply to it): the test's tag and an entry with its owner, reason, the hunt's rate, the date added and an expiry at most 14 days out, as "Flake quarantine" describes. Setting up the loop is the user's approval for these entries (core rules, "Tests and CI"), not for renewing them. When one of its entries has three days or fewer left, the loop takes that test again ahead of new ones; if it still finds no cause, it names the test to the user on the standing issue with the entry's expiry, renewal is the user's, and the loop does not take that test again until the user says so.
- **Repeat offenders.** A test the loop fixed that the hunt reports again within 14 days goes to the user, named on the standing issue with both PRs, and the loop does not take it again until the user says so.
- **Report.** Each run comments on the standing issue with the tests it took, their PRs, the quarantine entries it opened and the tests it skipped and why. Its PRs pass the same required checks and merge the same way as any other.

## Weekly CI report (opt-in)

Set this up when the user asks. A scheduled routine, weekly, runs this skill's audit read-only and posts the result to one standing issue. It gates nothing, and its findings become follow-ups and fixes through ordinary slices. For each workflow and job, it reports the PR median on the last attempt (and p90 when the week has enough runs to support it), their change over the previous week and over four weeks, runner minutes, and the nightly hunt's flake count over the week, against the spec's `CI budget:`. It also posts the week's runs and pushes per merged PR, the catch-up share, merge-path latency (median, and p95 when supported), cache usage against the limit (from the provider where GitHub's API reads empty), repeat push runs, and flake-hunt coverage, as the baseline measures them. It names any median over the budget and any job that grew by half or more over two weeks, and includes the conformance check's result. Confirm in one run that the routine has the `gh` access the audit needs. The lead reads the latest report at each milestone end, alongside the `/bosun-ci` audit, and its findings become follow-ups there.

## Implement through Bosun

For improvement requests, give `/bosun-brief` the selected outcome, baseline evidence, affected workflow/checks, expected benefit, and coverage invariants. Add these CI-specific done-conditions to the slice, scaled to the change:

- Required checks and supported test environments still execute for applicable events, and check names consumed by repository rules remain valid.
- Every removed or conditional check has an explicit coverage justification. Path selection accounts for shared dependencies, lockfiles, workflow changes, and merge-queue events when used. Check both matching and nonmatching changes; a skipped workflow must not leave a required check pending indefinitely.
- A change that adds or changes change-based selection or a path gate proves a skip cannot report green on a real change: a throwaway branch cut from the slice's branch breaks a file the selection should cover (a failing assertion in code a covered test exercises), a draft PR from it against the default branch runs the required check, and the check goes red. Where the workflows skip draft PRs, mark it ready for review instead, still without auto-merge, so the check runs rather than reporting skipped. This kind of push, made to see CI's verdict, is the one exception (core rules, "Tests and CI"), because the gate itself is under test. It is not a slice PR: never arm auto-merge on it, and it is not a red PR to fix (core rules, "Watching open PRs"). Record its run URL once the check reports, then close it unmerged and delete its branch, whatever the result. A green check means the gate let a real change through: that is a failed proof, and the slice fixes the gate before this done-condition can be met.
- Shards/matrices collectively retain the intended tests. Required failures still make CI fail: inspect `continue-on-error`, shell exit propagation, conditions, and any aggregate gate's handling of failed, cancelled, or unexpectedly skipped jobs.
- Changed caches/artifacts preserve compatibility, invalidation, and trust boundaries. Do not broaden token permissions or expose secrets to make an optimization work.
- The before/after comparison uses a stated method and evidence, or explicitly remains unmeasured pending hosted runs.
- An optimization that constrains how code or tests are written (an isolation opt-in, batched check jobs, what belongs in the base image, filtered installs) is recorded where the project's agents read it: its CLAUDE.md or AGENTS.md, or the spec's lessons. Otherwise later agents write code that quietly falls off the fast path.

Use the repo's existing checks and suitable workflow validation tools when available. A YAML parse is only a syntax check, not proof that GitHub will schedule jobs correctly. Exercise relevant event/condition cases and cold-cache behavior when the change depends on them. Bound experiments to the comparison needed; do not repeatedly rerun until a favorable result appears. Respect the request's scope for pushes and workflow dispatches, including any release side effects.

## Verify and report

Provide `/bosun-verify` with the diff base, baseline and candidate run URLs/attempts, exact validation commands, coverage mapping, and any unavailable evidence. Its independent review checks both preserved behavior and the claimed improvement. Keep correctness status separate from performance status: local checks passing cannot establish hosted speedup.

Compare runs with the same workflow scope, runner class, event, matrix, and equivalent workload; ideally use the same source workload apart from the CI change. Separate warm and cold caches and disclose unavoidable differences. Report sample counts and variation; if evidence is sparse or confounded, say so. Do not exclude failures or retries from the reliability/compute accounting to improve the result.

Deliver:

1. Main bottleneck and evidence.
2. Ranked recommendations for an audit, or the implemented change and coverage justification for an improvement.
3. Before/after elapsed time, runner minutes, and reliability observations where available; label each result measured, estimated, or unmeasured.
4. Validation evidence, limitations, and deferred work. In implementation mode, record durable findings in the existing spec and slice log; keep measurement-dependent conditions pending until evidence exists.
