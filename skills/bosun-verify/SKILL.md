# Bosun verify

The session that wrote the code is the wrong judge of it. This skill hands the judgment to a read-only agent at the resolved verifier effort (default `high`) with no memory of this session: `bosun-verifier-mobile` when the brief says `Surface: ios`, otherwise `bosun-verifier`.

## Effort selection

The verifier runs on Opus 5.5, including mobile verification (core rules, "Model"). If the spec's `Provider mode:` line names anything but `opus` (`fable` and `fable-opus` were removed in 0.24.0; `codex`, `fable-crew`, `astra-crew` and `astra` in 0.18.0), say to change it to `Provider mode: opus` or delete it, and stop before writes or spawn.

Resolve the effort before each launch: explicit `--effort <level>` for this invocation; otherwise `Verifier effort:` in the current slice's brief (its record, core rules, "Slice records", or an older spec's current-slice section); otherwise the top-level `Verifier effort:` near the top of the spec; otherwise `high`. Do not read settings from historical slices, logs, or quoted examples. Accept only `low`, `medium`, `high`, `xhigh`, `max`; missing flag values, unknown flags, duplicate conflicting values at the selected scope, or an invalid selected value stop verification before any writes or spawn. A one-run override never changes the spec default or the slice's setting. `/bosun-mode --verifier-effort <level>` changes the project default.

Run `python3 "<plugin root>/scripts/configure-claude-agents.py" --project "<project root>" --verifier-effort <resolved effort>` before spawning. Resolve the plugin root from this skill's location. This regenerates **both** project-local verifier definitions with real `effort` frontmatter on `claude-opus-5-5`; it also refreshes the scout. Always regenerate on the next invocation, so a one-run override does not become a default. Stop on setup errors. Use the local `bosun-verifier` or `bosun-verifier-mobile`, never the plugin-scoped `bosun:...` definition (which would ignore the generated effort). Confirm the local agent is loaded at the requested effort; if the agents directory is new to the running session, restart Claude Code first. A conflicting model environment override or an unavailable agent/model is a blocker, not a reason to silently use another verifier. No lead-session effort change is needed.

The first run uses the resolved effort. A delta re-check (every later run; core rules, "Finishing") runs at `medium`, or at the resolved effort when that is lower, except when the slice touches money, authentication or permissions, migrations, or security-sensitive code, where it keeps the resolved effort; an explicit `--effort` for that invocation still wins. Pass the delta effort to the configure script as that run's `--verifier-effort`. Record each run's effective effort in its verdict and in the slice's `Log:` line; never label a prompt-only request as an applied effort setting.

## Steps

0. Before a first run, check the pre-verify gate (core rules, "Self-check"). Its commands are the spec's `Pre-verify gate:` line, or, without one, the gate commands the brief's checks list. With no spec or brief, as when the user asks to verify work directly, they are the repository's own typecheck, lint, unit-suite, consistency and generated-file checks, which the lead finds and lists. When the line or the brief says `none`, or, with no spec or brief, the repository has none of these checks, the gate is empty and this step passes; say so in the prompt. Compute the fingerprint now, with the command in step 1. Each gate command must have a reported exit 0 on that fingerprint. If one is missing, red, or reported on another fingerprint, do not launch: the lead runs or fixes it first, and this is not a verify run. Otherwise, a brief under a spec that neither lists gate commands nor says `none` stops here until the lead adds one or the other, even when the repository has none of these checks. Delta re-checks and reruns skip this step.
1. Assemble a self-contained prompt. The verifier cannot see this conversation, so include:
   - The spec path, the slice's record path, and which slice or done-conditions to judge. If there is no spec, the done-conditions verbatim from the user's arguments or reconstructed from the request; say which.
   - The out-of-scope list.
   - The base to diff against (branch or commit).
   - The exact check commands and any setup they need.
   - The implementer's check results: for each check run after the last edit, on the slice's commit, the command and exit code, the working-tree fingerprint it ran on, and the fingerprint command, run in bash with the spec's and the slice record's repo-relative paths filled in (for an older slice with no record, drop the record's exclude), which writes no objects, does not refresh the index (`GIT_OPTIONAL_LOCKS=0`), and leaves out spec and record edits: `cd "$(git rev-parse --show-toplevel)" && { git rev-parse HEAD; GIT_OPTIONAL_LOCKS=0 git diff HEAD --binary --no-ext-diff --no-textconv -- . ':(exclude)<spec path>' ':(exclude)<record path>'; git ls-files -z -o --exclude-standard -- . ':(exclude)<spec path>' ':(exclude)<record path>' | while IFS= read -r -d '' f; do printf '%s\n' "$f"; git hash-object -- "$f"; done; } | git hash-object --stdin`. The checks are the core rules' self-check ("Finishing"), run after the last edit; the verifier does not rerun a whole-repository check or full suite reported passing on a matching fingerprint, and always runs the tests for the changed files. Say whether a required CI check runs the full end-to-end suite before merge.
   - On a delta re-check (every run after the first, except a rerun because a check could not run, which repeats that run's prompt plus a line naming that check): the findings ledger, every earlier run's findings by number, each with its latest status (open, resolved, or follow-up); the commit the previous run checked; the fix-diff command (`git diff <that commit>`; the lead commits the fix, then reruns the checks it could change on that commit); which checks were rerun for the fix, with results on the new fingerprint; and the instruction to work as a delta re-check (core rules, "Finishing").
   - Anything the verifier would otherwise misjudge: intentional deviations and their reasons, environment quirks, known pre-existing failures with evidence that they predate the change.
   - When any done-condition names a route or web screen: the implementer's `Evidence:` list (route, viewport when named, what was checked, screenshot path) and the app's launch command. The verifier re-checks only those done-conditions in Playwright, at the named viewport width when one is specified.
   - When a done-condition adds or changes a screen and names a board: the paths of the board images exported in this slice (core rules, "Design"), the widths to check (390, 768, 1024, 1280, and 1440 pixels, or the widths the project names), the states to check (empty, loading, error, hover, and focus, and the board's motion, including exits and reduced motion), the project's locked design rules, and the slice's approved departures. The verifier compares its screenshots with the board images and reports each difference that is not an approved departure as a finding, and each place the build breaks a locked rule.
   - When the brief says `Surface: ios`: the device name, build and install commands, bundle id, and the implementer's evidence lines (screen, device, what was checked, screenshot path).
   - In a lane (core rules, "Lanes"): the lane's stack command and number, to be used for every migration, end-to-end test, seed or data-resetting suite the verifier runs, and the rule that every screenshot and output path is absolute and inside the lane's worktree.
   - The implementer's test and CI statements: each existing test changed, skipped, or deleted and the done-condition that requires it, each check added under the core rules' "Corrections become checks" with the finding it came from, and, when a CI workflow changed, whether it adds or removes CI time. The lead states these.
   - The resolved verifier model and effort.
   - The spec's "Recurring verify failures" lesson, as kinds of defect to look for first, and the core rules' "What blocks" bar for FAIL, follow-ups and nits (core rules, "Finishing").
   - Which verify run of this slice this is (first, second or third), since the slice gets at most three (core rules, "Finishing").
   - Records riding along on this branch from other slices or decisions (core rules, "Records ride along"), by commit or file, so the verifier does not report them as unrequested changes.
2. When the brief says `Surface: ios`, launch the `bosun-verifier-mobile` agent with that prompt; otherwise launch `bosun-verifier`. While it runs, do not idle: draft the report, continue unrelated remaining work, or, under `Run policy: until blocked`, draft the next slice's brief, writing it into that slice's record only after the verifier returns. Do not edit files the verifier is reading.
3. Relay the verdict faithfully. Do not soften a FAIL.
   - FAIL: the lead fixes each in-scope finding, every instance of a named pattern included, adds the check the core rules' "Corrections become checks" asks for where a small one would have caught it (or records a bigger one as a draft done-condition), commits the fix, and then reruns only the checks it could change (core rules, Tests and CI), and the delta re-check's prompt carries their results on the new fingerprint. Then run this skill again as a delta re-check, at the effort "Effort selection" gives it. After two FAILs on the same finding, stop and report both positions to the user; under `Decisions: take recommendations`, the lead decides it instead (core rules, "Decisions") and stops at a third FAIL on the same finding. A third verify run that FAILs stops the slice whatever the findings (core rules, the verify limit in "Finishing"). Out-of-scope findings go in the report as follow-ups.
   - PASS WITH FOLLOW-UPS: report the follow-ups. Fix a reachable bug or security issue in the slice's own work in this slice (core rules, "Follow-ups and milestones") and run this skill again as a delta re-check on the fix before the PR. Drift, records, wording, and evidence that was only pending are the lead's to fix or confirm, rerunning the checks the fix could change, with no verify run. Pre-existing findings become `bug` follow-ups; a release-blocking one is named to the user at once and goes to the spec's human-checks (core rules, "What blocks"). Give every other follow-up the home that section names. On the third verify run, record such a bug as a `bug` follow-up instead of fixing and verifying a fourth time.
   - Nits the verifier lists for the slice's own diff: fix them before the PR or drop them; never write them down as follow-ups. Fix one without a further verify run only when the fix cannot change behavior (a comment, a name, formatting, wording), rerunning the checks it could change and naming it in the report; drop any other nit.
   - Not verified: done-conditions the verifier reports it could not check (no stack free, the machine too loaded, a tool unavailable) are not verified, whatever the verdict line says. Rerun this skill once the machine allows, which does not count toward the limit, or record the step as blocked (core rules, "Environment failures"). Never mark them verified.
   - PASS: report the verdict and the evidence lines. Screenshot paths the verifier reports are evidence; keep them in the report.
4. Record the verifier model and effective effort with the verdict in the slice's record and its `Log:` line. For each done-condition the verifier confirmed, mark it verified where it lives (the spec for a roadmap done-condition, the slice's record for one its brief defines) with a pointer to the evidence (commit, command, or file:line). Human-check conditions stay unverified and are listed for the user in the report.

Never let the verifier fix things, and never verify by re-reading your own work in this context; that is what the skill exists to avoid.
