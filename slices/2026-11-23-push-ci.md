A first version that failed each required check without a push trigger flagged crelaunch's security review; the rule now fails only when no required check runs on pushes.
- Fix round 1: each push run's group is `checks-push-<run_id>`; `push_covers` matches GitHub patterns (`*`, `**`, `?`, later `!` negations) and counts a path-filtered push as not covering; 16 cases pass, including `main*`, `ma?n`, `**` with `!main`, `branches-ignore: [ma*]`, `branches-ignore: [**]`, `release/*`, and `branches: [main]` with `paths`. Conformance results unchanged.
- Fix round 2: `branch_matches` reads `?` as zero or one and `+` as one or more of the preceding character and `[...]` as a set (`ma?n` matches `mn` and `man`, not `main`; `mai?n`, `mainn?`, `ma[a-z]n`, `mai+n` match `main`); conformance unchanged on bosun, rv-rez and crelaunch, and the PR-only base clone (with `--repo mckissinger/bosun`) still gives the push FAIL.
- `push_covers` cases (first version): no filter, `branches: [main]`, `branches: main`, `**` cover main; `branches: [release]`, tags-only, `branches-ignore: [main]` and a PR-only workflow do not.

## Follow-ups

- push-ci, 2026-11-23, drift: the conformance check's concurrency WARN only asks that a PR workflow cancels superseded runs; a no-queue project whose push runs share a group with `cancel-in-progress: true` passes, yet its main runs can be cancelled or replaced. Check that push runs to the default branch never share a cancelling or replacing group, in the next slice that touches the script.
- push-ci, 2026-11-23, bug: `push_covers` calls `startswith` on each branch filter, so a non-string entry (`branches: [2024]`, an empty item) crashes the check for a no-queue repo whose required check's workflow has it; coerce entries to strings.
- push-ci, 2026-11-23, bug: `branch_matches` turns `**` into `.*`, so `**/main` never matches `main` (GitHub's `**/` also matches zero directories), giving a false FAIL for a repo whose only push filter is `**/main`.
